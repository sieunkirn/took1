# 툭 챗봇은 플랫폼 대신 '얇은 LLM 층'을 얹자

**결론 요약.** 툭의 AI 뷰티 챗봇을 고도화할 때는 블로그에 나온 21개 "챗봇 플랫폼" 중 하나로 옮겨 가지 않는 것이 맞다. 그보다는 지금의 규칙 엔진(`src/lib/chat.js`)을 빠른 경로이자 안전망으로 그대로 두고, 그 뒤에 얇은 LLM 층을 붙이는 방식이 가장 잘 맞는다. 이 LLM 층은 이미 있는 함수(`parseMessage`, `recommendByColor`, `findById`, `findByBarcode`, `compareSummary`)를 도구(tool)로 호출하고, `{intent, product_ids, say_ko}` 형식의 구조화된 답만 낸다. 서버는 그 ID를 285개 DB와 대조해 검증하고, 제품 이름·가격·색 같은 사실은 언제나 DB에서 꺼내 화면에 그린다. 추천 조합은 다음과 같다. 에이전트 층은 **Vercel AI SDK 7**(Apache-2.0)이고, 검색은 처음엔 벡터 RAG 없이 **LLM이 조건(필터)을 뽑고 기존 CIEDE2000으로 재정렬**한다. 모델은 **Qwen3.5 / Gemma 4**(둘 다 Apache-2.0)로 시작하되 한국어 뉘앙스 후보로 Kanana-2를 함께 비교하고, 평가는 **Promptfoo + Langfuse**(둘 다 MIT)로 한다. 음성은 당장은 Web Speech를 보강해 쓰고, 나중에 **Qwen3-ASR / faster-whisper + Silero VAD**로 옮기는 단계 계획을 권한다. 블로그 목록은 2026년 11월 기준 상당수가 보관(archived)·종료·정체 상태다. 살아 있는 것 중에서도 툭이 코드로 이미 할 수 있는 일 이상을 해 주는 플랫폼은 없다. Flowise처럼 회사에 인수된 로우코드 플랫폼이 2026년 8월에 종료된 사례도 있어, 플랫폼 종속은 실제로 일어나는 위험이다 ([Future of Flowise](https://github.com/FlowiseAI/Flowise/discussions/6727)).

### 에이전트 층은 Vercel AI SDK 7, 직접 API 호출도 충분히 가능하다

**Vercel AI SDK 7**(`ai` 7.0.162, 직접 의존성 3개, 주간 다운로드 약 4300만)을 1순위로 꼽는다 ([npm](https://registry.npmjs.org/ai/latest)). 이유는 한 번의 `generateText` 호출에 `tools`와 `output: Output.object({ schema })`를 같이 넣을 수 있다는 점이다. 그러면 "도구로 제품을 찾고 → 정해진 모양의 답을 낸다"가 한 흐름으로 끝난다. 검증에 실패하면 `NoObjectGeneratedError`가 나므로 그때 규칙 엔진으로 넘기면 된다. `Output.choice`로는 값을 정해진 목록 안으로 묶을 수 있다 ([AI SDK 문서](https://ai-sdk.dev/docs/ai-sdk-core/generating-structured-data)). 제공사를 쉽게 바꿀 수 있다는 점도 크다. `@ai-sdk/openai-compatible`를 쓰면 Ollama나 vLLM 같은 로컬 모델에도 같은 코드로 붙는다 ([npm](https://registry.npmjs.org/@ai-sdk%2Fopenai-compatible/latest)). 대신 주의할 점이 둘 있다. v7은 **Node.js 22 이상과 ESM 전용**을 요구하고 ([마이그레이션 가이드](https://ai-sdk.dev/docs/migration-guides/migration-guide-7-0)), 메이저 버전이 2025-07, 2025-12, 2026-06으로 약 5~6개월마다 바뀌었다 ([npm](https://registry.npmjs.org/ai)). 그래서 버전을 고정하고, 프레임워크 코드는 `src/lib/llm/agent.js` 한 파일 안에만 가둬 두기를 권한다.

2순위는 **LangChain.js v1 `createAgent`**다. 스키마 검증에 실패하면 오류 내용을 모델에게 돌려보내 다시 시도하게 하는 기능(`handleError`)이 기본으로 들어 있다 ([LangChain 문서](https://docs.langchain.com/oss/javascript/langchain/structured-output)). 나중에 대화 상태를 그래프로 오래 저장해야 하면 LangGraph로 넓힐 수도 있다. Mastra는 사용자 선호를 기억하는 "working memory"가 가장 잘 갖춰져 있어 개인화와 잘 어울린다 ([Mastra memory](https://mastra.ai/docs/memory/overview)). 하지만 직접 의존성이 30개이고 저장소 어댑터도 따로 필요하다. 툭의 개인화 정보(톤, 선호 피니시, 입술 고민)는 작은 세션 객체 하나로 충분하므로 지금은 과하다. 피해야 할 것도 분명하다. **Claude Agent SDK**는 Claude Code 실행 파일을 돌리는 라이브러리이고 파일·셸 도구를 내장하고 있어, 키오스크 챗봇에는 오히려 위험하다 ([Agent SDK 개요](https://code.claude.com/docs/en/agent-sdk/overview)). **LlamaIndex.TS**는 2026년 4월에 보관되었다 ([GitHub](https://github.com/run-llama/LlamaIndexTS)). 덧붙여 Anthropic은 "LLM API를 직접 쓰는 것부터 시작하라, 프레임워크는 프롬프트를 가려 디버깅을 어렵게 한다"고 권고한다 ([Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)). 도구 4~6개짜리 루프라면 `openai` 클라이언트(의존성 0개)로 직접 짜는 것도 충분히 현실적인 선택지다 ([npm](https://registry.npmjs.org/openai/latest)).

### 285개 제품에는 벡터 RAG보다 "조건 추출"이 먼저다

"건조한 입술에 촉촉한 거"나 "여름 휴가 때 바를 만한 거" 같은 질문은 의미 검색 문제가 아니다. 피니시, 색 계열, 가격 같은 속성을 고르는 문제다. 그래서 첫 단계는 LLM이 자유로운 한국어를 `{finish:[], color_family:[], price_max, color_hint}` 같은 필터 JSON으로 바꾸고, 기존 필터와 `recommendByColor`가 결과를 정하게 하는 것이다. 이것은 LangChain의 SelfQueryRetriever와 같은 패턴인데 ([LangChain.js self-query](https://js.langchain.com/docs/how_to/self_query)), 툭은 이미 `parseMessage`가 같은 슬롯을 뽑고 있다. 따라서 그 함수의 출력 형식을 그대로 도구 입력 스키마로 쓰면 된다. 단, 소규모 카탈로그에서 이 방식이 벡터 RAG보다 낫다는 공개 벤치마크는 없다. 이 판단은 엔지니어링 판단이다.

벡터 검색이 쓸모 있어지는 시점은 리뷰나 성분 같은 긴 텍스트가 들어오고 문서가 수천 개로 늘어날 때다. 예를 들어 올리브영이 4700만 건 리뷰에 LLM을 적용하겠다고 한 것과 같은 상황이다 ([한국경제](https://www.hankyung.com/article/2026030238111)). 그때는 Node 안에서 돌아가는 **Orama**(Apache-2.0, BM25·벡터·하이브리드·필터를 한 번에 지원) 또는 **LanceDB**(내장형, 전문 검색 + 벡터 + RRF 지원)를 고른다 ([Orama](https://github.com/oramasearch/orama), [LanceDB](https://lancedb.com/docs/search/hybrid-search)). 한국어 임베딩은 MTEB(kor) 검색 1위가 KURE-v2(nDCG@10 0.816, Apache-2.0)다. 하지만 이 모델은 토큰마다 벡터를 따로 저장하는 ColBERT 방식(late-interaction)이라 다루기가 번거롭다. 그래서 문장 하나에 벡터 하나를 쓰는 KURE-v1(MIT)이나 bge-m3(0.75대)가 더 실용적이다 ([KURE-v2](https://huggingface.co/nlpai-lab/KURE-v2), [KURE-v1](https://huggingface.co/nlpai-lab/KURE-v1)). bge-m3는 transformers.js용 ONNX 파일이 이미 있다 ([Xenova/bge-m3](https://huggingface.co/Xenova/bge-m3/blob/main/README.md?code=true)). 한국어 키워드 검색(BM25)은 형태소 분석 없이는 "촉촉한/촉촉해서"를 같은 말로 묶지 못한다. 그래서 **Kiwi**(0.23.2 이후 Apache-2.0, 공식 WASM 패키지 `kiwi-nlp`)로 미리 토큰을 나눠 두기를 권한다 ([Kiwi](https://github.com/bab2min/Kiwi)). 다만 285개 규모에서는 "촉촉→수분/글로시" 같은 동의어 표 하나가 형태소 분석기보다 효과가 클 수 있다.

### 모델은 Apache-2.0 두 계열로 시작하고, 한국 모델은 비교군으로 둔다

**Qwen3.5**와 **Gemma 4**는 둘 다 Apache-2.0이다. 둘 다 Ollama에 도구 호출 태그가 붙은 공식 빌드가 있고, 4비트 기준 Qwen3.5-35B 22GB, Gemma 4 12B 약 8GB 수준이라 GPU 한 장이나 Mac 한 대에서 돌아간다 ([Ollama qwen3.5](https://ollama.com/library/qwen3.5), [Ollama gemma4](https://ollama.com/library/gemma4)). Gemma 4가 Apache-2.0으로 바뀐 것은 Google 발표로 확인했다 ([Google](https://x.com/Google/status/2039736229600612767?lang=en)). Qwen3.5의 라이선스는 2차 출처로만 확인했다. 두 모델 모두 한국어 도구 호출 품질을 잰 공개 수치는 찾지 못했다. **Kanana-2-30B-A3B**는 KMMLU 67.3, BFCL-v3 Live 74.3을 직접 보고한 한국어 모델이다 ([HF](https://huggingface.co/kakaocorp/kanana-2-30b-a3b-instruct)). 한국어 뉘앙스로는 가장 기대되지만 라이선스에 조건이 붙는다(아래 라이선스 절 참고). **EXAONE 4.0**은 한국어와 도구 호출 모두 좋지만 라이선스가 비상업(NC)이다 ([HF](https://huggingface.co/LGAI-EXAONE/EXAONE-4.0-1.2B)). 1~4B 소형 모델은 EXAONE 1.2B의 BFCL 55.7에서 보듯 여러 턴 도구 호출이 불안하다. K-EXAONE(236B), Solar Open(100B), A.X K1(519B) 같은 소버린 모델은 H200·A100 GPU 4장 이상이 필요한 데이터센터급이다 ([K-EXAONE](https://huggingface.co/LGAI-EXAONE/K-EXAONE-236B-A23B), [Solar Open](https://huggingface.co/upstage/Solar-Open-100B)). 실무 요령은 이렇다. 엔드포인트를 OpenAI 호환 하나로 통일해 두고, 같은 평가 세트로 Qwen3.5·Gemma 4·Kanana-2와 상용 API 하나를 A/B로 비교한 뒤에 고른다.

멀티모달은 얼굴 사진을 LLM에 넘기는 방식으로 하지 않기를 권한다. Qwen3.5는 비전 태그가 붙어 있지만, 툭은 이미 MediaPipe와 Lab 변환으로 입술 색을 숫자로 갖고 있다. 이 숫자(`hex`, `lab`, 피부 톤 추정값)를 도구 인자로 넘기는 편이 정확하고, 재현할 수 있고, 개인정보 면에서도 안전하다. 업계 선례도 같은 구조다. 아모레퍼시픽 뷰티 컨시어지는 퍼스널컬러 진단을 별도 모듈로 두고 ([코스인코리아](https://www.cosinkorea.com/mobile/article.html?no=57514)), 로레알 Beauty Genius는 자사 750여 개 제품이라는 닫힌 카탈로그 안에서만 추천한다 ([L'Oréal Paris](https://www.lorealparisusa.com/beautygenius)).

### 음성은 Web Speech를 보강하고, 서버 STT는 다음 단계로 미룬다

iPad Safari의 Web Speech는 세션이 저절로 끊기거나 첫 시도가 실패한다는 보고가 있다. web-features는 Safari를 아예 "미지원"으로 분류한다 ([iOS Web Speech 팁](https://lilting.ch/en/articles/ios-webspeech-api-tips), [web-features](https://web-platform-dx.github.io/web-features-explorer/features/speech-recognition)). 당장은 누르고 말하기(push-to-talk), `continuous:false` + 자동 재시작, 마이크 예열로 버티면서 `normalizeSpoken`의 자모 거리 교정을 그대로 쓴다. 서버로 옮길 때의 후보는 **Qwen3-ASR-1.7B**(Apache-2.0, vLLM 스트리밍, 프롬프트에 브랜드·색 이름 목록을 넣어 인식을 유도할 수 있음)와 **faster-whisper large-v3/turbo**(MIT)다. 소규모 FLEURS 한국어 표본에서 문자 오류율(CER)은 각각 3.34%, 4.08%/4.60%였다 ([PR #740](https://github.com/zkaelxz/U00/pull/740)). 그런데 즉흥 발화(KsponSpeech)에서는 Whisper CER이 11~17%로 뛴다 ([ENERZAi](https://www.edge-ai-vision.com/2025/11/small-models-big-heat-conquering-korean-asr-with-low-bit-whisper/), [HF 카드](https://huggingface.co/o0dimplz0o/Whisper-Large-v3-turbo-STT-Zeroth-KO-v2)). 숫자와 영문 오류가 많다는 점도 확인됐다. 그래서 서버 STT로 바꾸더라도 기존 교정 층은 후처리로 계속 둬야 한다. VAD는 **Silero VAD**(MIT, 30ms 조각을 1ms 미만에 처리)가 표준이다 ([GitHub](https://github.com/snakers4/silero-vad)). TTS는 상업 이용이 가능한 **MeloTTS**(MIT, CPU 실시간)와 **Fun-CosyVoice 3**(Apache-2.0, 약 150ms 스트리밍, GPU 필요)이 안전하다 ([MeloTTS](https://github.com/myshell-ai/MeloTTS), [CosyVoice](https://github.com/FunAudioLLM/CosyVoice)). 끼어들기(barge-in)나 자연스러운 말 차례 감지가 필요해지면 **Pipecat**(BSD-2, JS 클라이언트 제공)으로 툭의 LLM 층을 감싸면 된다 ([Pipecat](https://github.com/pipecat-ai/pipecat)). Qwen3-Omni 같은 음성→음성 모델은 제품명·가격을 도구로 정확히 말하게 통제하기 어려워 아직 이르다 ([Qwen3-Omni](https://arxiv.org/html/2509.17765v1)).

### 가드레일은 구조로, 평가는 Node 안에서

툭에서 환각을 막는 핵심은 가드레일 라이브러리가 아니라 구조다. 첫째, LLM에게는 읽기 전용 도구만 준다. 둘째, 답에 담긴 ID는 DB와 "이번 턴에 도구가 돌려준 ID" 양쪽에 다 있어야 한다. 셋째, 사실은 DB에서 렌더링한다. 이렇게 하면 OWASP LLM01(프롬프트 인젝션)과 LLM06(과도한 권한) 위험이 대부분 사라진다 ([Promptfoo OWASP](https://promptfoo.dev/docs/red-team/owasp-llm-top-10/)). 평가는 **Promptfoo**(MIT, Node 기반, 2026년 3월 OpenAI가 인수)로 한다. `is-json` 스키마 검사, `javascript` 사용자 정의 검사, `tool-call-f1`, 도구 호출 순서(trajectory) 검사, `llm-rubric`을 쓸 수 있고, 규칙 엔진과 LLM 층을 한 설정 안에서 나란히 비교할 수 있다 ([Promptfoo assertions](https://www.promptfoo.dev/docs/configuration/expected-outputs/)). 실행 기록 추적은 **Langfuse**(핵심 기능 MIT, 2026년 1월 ClickHouse가 인수, 자체 호스팅 가능)로 한다 ([ClickHouse](https://clickhouse.com/blog/clickhouse-acquires-langfuse-open-source-llm-observability)). 한국어 안전 분류기가 필요하면 **Kanana Safeguard**(Apache-2.0, 인젝션 탐지용 2.1B 모델 포함)가 맞다 ([Kakao](https://www.kakaocorp.com/page/detail/11568?lang=ENG)). 반면 NeMo Guardrails와 Guardrails AI는 Python 서비스가 따로 필요하다. Guardrails AI의 npm 패키지는 0.1.x이고 Python 브리지에 의존한다 ([npm](https://www.npmjs.com/package/@guardrails-ai/core)). Llama Guard 4는 한국어를 공식 지원하지 않는다 ([CultureGuard](https://arxiv.org/html/2508.01710v4)).

### 뷰티 도메인 자산은 "가져다 쓰기"보다 "직접 구현"이 안전하다

공개된 퍼스널컬러 코드는 취미 수준이 대부분이다. 가장 많이 알려진 한국 저장소 ShowMeTheColor는 Lab b*로 웜/쿨을, HSV 채도로 계절을 나눈다. 그런데 정확도를 스스로 여름/겨울 약 50%라고 밝히고 있고, 라이선스가 표시되어 있지 않다 ([GitHub](https://github.com/starbucksdolcelatte/ShowMeTheColor)). 그래서 코드를 복사하지 말고, 같은 아이디어를 툭의 `hexToLab`·`deltaE2000` 위에 직접 구현해 `estimate_tone()` 도구로 만들기를 권한다. 화면과 음성에서는 결과를 "진단"이 아니라 "참고 제안"으로 말해야 한다. 메이크업 전이 모델 EleGANt는 CC BY-NC-SA 4.0이라 상업적으로 쓸 수 없다 ([GitHub](https://github.com/Chenyu-Yang-2000/EleGANt)). 툭의 MediaPipe 입술 마스크 + 색 합성 방식이 법적으로 더 깨끗하다. 한국 화장품 색상 공개 DB는 찾지 못했으므로, 285개 올리브영 JSON 자체가 툭의 가장 중요한 도메인 자산이다.

## 규칙 엔진을 지키는 4단계 로드맵

설계의 원칙은 하나다. **LLM은 "무엇을 찾을지"와 "어떻게 말할지"만 정하고, "무엇이 있는지"는 언제나 DB가 정한다.** 대화형 추천 연구들도 프롬프트만으로 만든 LLM 추천기는 없는 상품을 지어낸다고 정리한다. 실제 카탈로그에 묶어 두는 것(retrieval/anchoring)이 해법이라고 본다 ([arXiv 2510.27157](https://arxiv.org/pdf/2510.27157), [arXiv 2305.07961](https://ar5iv.labs.arxiv.org/html/2305.07961)). 아래 단계의 파일·함수 이름 중 `parseMessage`, `answer`, `compareSummary`, `recommendByColor`, `findById`, `findByBarcode`, `normalizeSpoken`, `hexToLab`, `deltaE2000`은 현재 코드에 실제로 있는 이름이다. `src/lib/llm/` 아래 이름은 새로 만들 것에 대한 제안이다.

**0단계: 평가 세트부터 만든다(1~2주).** 한국어 발화 150~300개에 의도, 기대하는 도구, 기대하는 제품 ID(또는 "ΔE00 ≤ X" 같은 조건), 그리고 `must_not`(나오면 안 되는 사실)을 붙인다. 범주는 색 추천, 브랜드·가격 조건, "그중에 제일 싼 거" 같은 후속 질문, 비교, 바코드, 착용("이거 발라줘"), DB에 없는 제품, 도메인 밖 질문(날씨·피부 질환), 인젝션("이전 지시 무시하고"), STT 오류가 섞인 문장이다. 그다음 Promptfoo에서 `answer()`를 provider로 감싼 기준선을 먼저 잰다. 이 점수가 이후 모든 단계를 통과시킬지 판단하는 기준이 된다.

**1단계: LLM을 대체 경로로 붙인다.** `src/lib/llm/router.js`의 `route(message, session)`가 먼저 `parseMessage`를 부른다. 슬롯이 충분히 잡히고 아는 의도라면 지금처럼 `answer()`로 바로 답한다(빠른 경로). 슬롯이 비었거나 모르는 표현이면 `src/lib/llm/agent.js`의 `runAgent()`로 넘긴다. 도구는 기존 함수를 감싼 `search_products(filters)`(`parseMessage` 슬롯 형식 재사용), `recommend_by_color(hex, finish, limit)`(`recommendByColor`), `get_product(id)`(`findById`), `lookup_barcode(code)`(`findByBarcode`), `compare_products(ids)`(`compareSummary`), `get_last_results()`(세션의 직전 목록, "두 번째 거" 처리용)이고, 모두 읽기 전용이다. 최종 출력은 zod 스키마 `{intent, product_ids, say_ko}`다. `validate.js`에서 ID가 DB에도 있고 이번 턴 도구 결과에도 있는지 확인하고, `say_ko`에 가격·숫자·브랜드명이 직접 들어 있지 않은지 검사한다. `render.js`는 `{{p1.name}}`, `{{p1.price}}` 같은 자리 표시자를 DB 값으로 채우고, 카드·TTS 문장도 서버에서 조립한다. 시간 초과, 스키마 실패, 모르는 ID, 안전 분류기 경고가 생기면 무조건 `answer()`의 결과로 돌아간다. 그래서 키오스크는 언제나 답을 한다.

**2단계: 개인화와 색 정보를 도구로 연결한다.** 세션 객체 `profile = {tone, preferredFinish, lipConcern, priceMax, triedIds}`를 router가 관리하고, 도구 컨텍스트로 넣어 준다. AI SDK 7은 도구별 `context`/`contextSchema`를 지원한다 ([마이그레이션 가이드](https://ai-sdk.dev/docs/migration-guides/migration-guide-7-0)). 가상 착용 화면에서 고른 `selectedHex`와 새로 만들 `estimate_tone(lab)` 결과도 같은 profile에 쌓아, "아까 발라 본 것보다 덜 진한 거" 같은 요청을 `deltaE2000` 기반 도구 호출로 바꾼다. 이 단계에서 LLM 조건 추출용 동의어 표와, 필요하면 Kiwi 토큰화를 추가한다.

**3단계: 음성과 검색을 필요할 때만 키운다.** Safari 안정성, 매장 소음, 개인정보가 실제 문제가 되면 STT를 서버(Silero VAD → Qwen3-ASR 또는 faster-whisper, 브랜드·색 이름 목록을 프롬프트로 제공 → `normalizeSpoken`)로 옮긴다. 이와 별개로 리뷰·성분 같은 텍스트 데이터가 들어오면 Orama 또는 LanceDB + KURE-v1/bge-m3 하이브리드 검색을 `search_products` 도구 안쪽에 추가한다. 겉으로 보이는 도구 이름과 형식은 바꾸지 않으므로 1~2단계 코드는 그대로 둔다. 매 단계는 0단계 세트에서 "의도 정확도가 규칙 엔진 이상이고, 지어낸 ID·사실이 0건"일 때만 통과시킨다.

## 상업적 이용 전에 확인할 라이선스 함정

Apache-2.0, MIT, BSD 계열은 상업적으로 쓰는 데 걸림돌이 거의 없다. 이번 추천에서 이 계열은 AI SDK, LangChain, Orama, Kiwi, KURE-v2, Qwen3.5, Gemma 4, Qwen3-ASR, faster-whisper, Silero VAD, MeloTTS, CosyVoice 3, Pipecat, Promptfoo, Langfuse 핵심 기능, Kanana Safeguard다. 반면 조건이 붙는 것이 여럿 있다. **Kanana-2**는 자체 서비스에 쓰는 것은 허용하지만 세 가지 제약이 있다. "Powered by Kanana"를 표시해야 하고, 월 사용자 1000만 명을 넘으면 별도 계약이 필요하며, 모델을 넣은 온프레미스·온디바이스 제품을 재판매하는 것이 제한된다 ([Kanana License](https://huggingface.co/kakaocorp/kanana-2-30b-a3b-instruct/blob/main/LICENSE)). 툭이 키오스크 기기 자체를 판매하게 되면 마지막 조항에 걸릴 수 있다. **HyperCLOVA X SEED**는 "Powered by HyperCLOVA X" 표시를 요구하고, 파생 모델 이름을 그 이름으로 시작해야 한다 ([LICENSE](https://huggingface.co/naver-hyperclovax/HyperCLOVAX-SEED-Think-32B/blob/main/LICENSE)). **EXAONE 4.0**은 비상업(NC)이므로, 상업적으로 쓰려면 라이선스를 받은 호스팅(FriendliAI 등)을 거쳐야 한다. 그 밖에 Typebot(FSL), Dify(멀티테넌트·로고 조건), Open WebUI(브랜딩), Rasa Pro(대화 수 제한), LiveKit turn detector(LiveKit Model License)도 조건이 있다 ([PyPI](https://pypi.org/project/livekit-plugins-turn-detector/1.4.1/)). XTTS-v2·F5-TTS·Fish Speech와 EleGANt는 비상업 라이선스다 ([localaimaster](https://localaimaster.com/blog/best-local-tts-models)). Supertonic은 가중치가 OpenRAIL-M이고 저장소가 보관 조직으로 옮겨졌다 ([GitHub](https://github.com/supertone-oss-archive/supertonic/wiki)). Silero VAD는 MIT로 알려져 있지만 배지 하나가 CC BY-NC로 표시되어 있다. 이처럼 라이선스 표기가 서로 어긋나는 경우가 있으니, 도입 직전에는 각 저장소의 LICENSE 파일을 직접 확인해야 한다.

아직 풀리지 않은 질문도 분명히 적어 둔다. Qwen3.5·Gemma 4·Kanana-2의 **한국어 도구 호출 품질을 같은 조건에서 비교한 공개 자료가 없다.** 그래서 모델 선택은 0단계 평가 세트로만 정할 수 있다. 소규모 카탈로그에서 조건 추출 방식이 벡터 RAG보다 낫다는 주장도 근거가 엔지니어링 판단뿐이다. 한국어 STT 수치는 깨끗한 낭독 음성 기준이라 매장 소음 환경에서의 성능은 모른다. 지금 iPad Safari의 Web Speech가 기기 안에서 처리되는지, 서버로 보내지는지도 확인하지 못했다. Golem·Juji·GPT-2·QnA Maker 은퇴일은 1차 출처를 확보하지 못했다. 업계 선례(올리브영 키오스크, 아모레퍼시픽, 로레알) 중 환각 통제 방법을 공개한 곳도 없었다.

## Conclusion

이번 조사로 바뀐 관점은 하나다. "어떤 챗봇 플랫폼으로 갈아탈까"는 2026년에는 맞지 않는 질문이다. 블로그 시대의 플랫폼은 대부분 사라졌다. 살아남은 LLM 플랫폼도 툭이 가장 중요하게 여기는 "DB 밖 제품 금지"를 대신 보장해 주지 않는다. 오히려 툭이 이미 가진 규칙 엔진, 색 계산, 발음 교정이 다른 회사의 LLM 비서와 구별되는 차별점이자, LLM을 안전하게 붙일 수 있게 해 주는 토대다. 올리브영의 2026년 7월 매장 AI 키오스크도 상품 정보·재고·피부 타입 추천에 머물러 있다 ([CJ Newsroom](https://newsroom.cj.net/olive-young-ai-in-store-services/)). CIEDE2000 입술 색 매칭과 실시간 착용을 대화에 묶는 것이 툭만의 자리다.

따라서 지금 가장 값어치 있는 작업은 새 라이브러리를 고르는 일이 아니라 0단계의 한국어 평가 세트다. 이 세트가 있어야 모델·STT·검색을 바꿀 때마다 "더 나아졌고, 지어낸 것은 0건"이라는 사실을 숫자로 확인할 수 있다. 프레임워크가 반년마다 메이저 버전을 바꾸는 환경에서는 코드보다 이 세트가 더 오래 남는 자산이다.
